MirrorNotes performance audit

The big win is real and it is in one place. At 5,000 entries the Entries tab spends most of its main-thread time re-reading every entry's stored fields to decide whether anything changed. A 60-line prototype already halves that time. A shared change counter should remove most of the rest. Launch is fine. The cost grows with the size of the journal: it is large from about 2,000 entries, while under about 1,000 it fits inside a frame and nobody would notice (estimated from the 5,000-entry numbers, which scale linearly). It is still worth fixing now, because every year of journaling adds 365 entries to it. A full UI redesign is not needed; four targeted UI changes are listed below.

Method

How the numbers were taken

Mac app, Apple-silicon laptop, synthetic 5,000-entry journal (--perfSeed=5000: one entry a day, every tenth with a 180 KB photo, synthetic text only). The scripted scenario opens Entries and runs six searches. Signposts come from tools/perf/mac_baseline.sh; attribution from a 22-second Time Profiler trace of the same scenario. Each baseline ran twice; runs agreed within 2%, except launch, which varied by about 5%.

Builds were Debug and Debug compiled with -O. They differ by under 10% (deps 71 vs 67 ms), so the cost is not Swift code speed. It is SwiftData property access: every @Model getter goes through observation registration and key-path lookups.

Not measured: the iPhone. The same code runs there, on a slower CPU, so expect these numbers to be larger on an iPhone 14 Pro, but nobody has measured them. Also not measured: the app-foreground widget work and Gemma model load, because perf runs skip both on purpose (they post notifications and load the model).

The same pattern lives in four more places

Every screen that needs to notice edits hashes the whole journal inside body: InsightView.entryCacheKey (mood and date of every entry and check-in), MoodTimelineView.moodDataCacheKey, CalendarHeatmap (entries.map(\.encryptedMood).hashValue, also on the Entries tab), and the list above. Seven views hold a full-history @Query of Entry, including Settings and the entry reader. Opening any entry loads all 5,000 rows and scans them twice per render for On This Day.

Two costs nobody has measured yet

  • Every app foreground, updateWidgetHeatmaps fetches every entry and check-in, decrypts every mood and calls WidgetCenter.reloadAllTimelines(); syncNudgeToWidget fetches every entry to read the newest one. Photos are stored inside the entry row, so touching any field loads the row's photo bytes too.
  • Gemma reloads for each generation (service = nil in runGemma's defer). Reflection, follow-up chip, digest and report each load the 1B model again. This only affects devices without Apple Intelligence, but there it is likely the largest wait in the app.
Plan

Performance work, in order

Each step names its baseline, the change, the expected gain and the signpost that proves it. Steps 1–3 cover the measured problem. Steps 4–8 need a baseline first.

  1. Keep the cheap signature and compute it once per pass

    measured

    The prototype hashes each encrypted field's length, first 40 and last 28 bytes. Every encryption draws a fresh random nonce at the front and ends in the GCM tag, so any rewrite changes both. contentSignature remembers each entry's signature and item(for:) reuses it. Diff: .claude/audit-2026-11-04-entrylist-prototype.diff. Result: entries.snapshot 253 → 53 ms, entries.search 425 → 253 ms. One caveat to test: if encryption ever fails, the field is stored as plaintext, and an edit in the middle of a long plaintext field with the same length would be missed.

  2. One journal change counter instead of per-render hashes

    estimate

    A small @Observable JournalRevision that goes up on ModelContext.didSave from any context, on CloudKit's remote-change notification, and after restore or erase. The Entries list, Insights, Mood Timeline and the calendar key their .task(id:) on it instead of hashing every entry in body. Baseline 67–75 ms per body evaluation; expected under 1 ms, which also removes the ~1,500 samples of observation bookkeeping those reads cause. Verify with entries.deps and the hang count. Ship it together with step 1: step 1 alone makes entries.deps slightly slower (67 → 75 ms) because it also rebuilds the per-entry table on every render.

    The counter can move before @Query has refetched, so the snapshot could rebuild from the old array and then miss the refreshed one. Acceptance tests before it ships: (a) change an existing entry's mood and date locally, (b) a CloudKit import that changes an existing entry, (c) a save from a background context (Siri intent, voice transcription). Each must update the row, the calendar and Insights without another save.

  3. Rebuild only the entries that changed

    estimate

    didSave carries the inserted, updated and deleted identifiers. Drop those from the decrypt cache and keep the rest; run the full signature pass only after a CloudKit import. Expected: entries.snapshot after a local edit drops from 53 ms toward the cost of filtering and grouping value types.

  4. Foreground widget work: metadata only, only when the journal changed

    unmeasured

    Add signposts active.widgetHeatmaps and active.syncNudge and measure on the 14 Pro first. Then fetch with propertiesToFetch = [\.createdAt, \.encryptedMood], skip the rebuild when JournalRevision hasn't moved since the last write, use fetchLimit for the newest entry, and reload only the widget kinds whose data changed.

  5. Entry reader: no full-journal query

    unmeasured

    Replace EntryDetailView's allEntries query with targeted fetches (a date-range fetch per past year for On This Day, the reflection's day window for the Mac pane) computed once in a .task. Same for Settings' word total and streak (propertiesToFetch = [\.wordCount, \.createdAt]). Signpost reader.open.

  6. Keep Gemma loaded for a short while

    unmeasured

    Signpost gemma.load and gemma.generate on the 14 Pro with Apple Intelligence off. If load is a large share, keep the model for about a minute after a generation while the app is in the foreground, and release it on background (the GPU gate already does) and on memory warning. Peak memory is the trade, so measure that too.

  7. A read model for the whole app

    later

    If steps 1–5 leave hangs above 100 ms on the phone, build JournalIndex: a background @ModelActor that keeps one value row per entry (dates, preview, mood, tags, flags, search text) and updates from the change counter. Screens read rows, never @Model objects across the whole journal. This is the large refactor; do it only if the numbers ask for it.

  8. Photos out of the row

    decision

    @Attribute(.externalStorage) on the photo and voice fields would stop full-row loads from carrying image bytes. It is a schema change on a synced model, so it needs its own migration and CloudKit test before anyone ships it.

Incident

The perf script launched the installed app

On this Mac, xctrace record --launch started /Applications/MirrorNotes.app, the App Store build, instead of the unsigned Debug copy, because both carry the bundle id com.lokesh.mirror. Release ignores --perfSeed, so the installed app opened your real Mac journal, as an ordinary launch would, twice for up to 25 seconds each, and once more for about a minute: a new guard caught it within 5 seconds but only stopped one of its two processes, and the other ran until it was killed by hand. Nothing left the device; it ran its normal app-active work, which can include today's reflection if one was due.

Changing the copy's bundle id did not help. The script now records all processes, starts the Debug binary by path itself, aborts if any MirrorNotes outside the build folder is running with the seed argument, and warns if no perfSeed signpost appears. It also takes PERF_OPTIMIZED=1 for a -O build. All numbers on this page come from the fixed script.

Design

UI and UX: targeted changes, no redesign

Two reviews shipped in the last three weeks (21 Oct design review, 24 Oct UI pass). A new visual system now would undo work that hasn't had time to land with users. What 15 November changes is who sees which screens, and the slowness above is the most visible UX problem in large journals. This pass looked at simulator captures of Insights, Entries, Write and the paywall as a Free user, and at the code. A system Apple ID prompt covered part of each capture and couldn't be dismissed from the command line, so the visual review is partial.

  1. Free Insights is mostly locks

    After the one free reflection, a Free user's Insights tab is a stack of "Core required" cards and "Core" badges: digest, Ask, timeline, monthly report. Proposal: lead Free Insights with what Free keeps (streak, this week's moods, saved reflections) and gather the locked features into one "What Core adds" card at the end, with one upgrade button. Same change in Sentinel's Briefing tab.

  2. Search must keep up with typing at any size

    Today each keystroke in Entries search re-hashes the journal on the main thread (step 2 above). On a large journal that is visible typing lag. Fixing it is the single UX change with the widest reach.

  3. "53w" on entry rows

    The row's word count reads as "53 weeks" at a glance. Show "53 words" in Classic, or drop it from the row and keep it in the reader. Sentinel's mono style can keep a short form ("53 W").

  4. Paywall: two accents

    The Core header is the purple brand gradient; the Start Free Trial button below it is rose. Pick one so the button reads as part of the plan card. Needs a clean capture to confirm the colours.

Not reviewed this time: Settings structure (about nine screens, four Sentinel-only), Mac, iPad, Dynamic Type at accessibility sizes. The 24 Oct pass covered Dynamic Type and VoiceOver.

Decisions

Five choices

Answered 4 November: the owner chose 3.1.8 instead of 3.1.9; the other recommendations were taken as given (steps 1–3 now, Gemma and photos later, the Free Insights card built). The paywall button colour is still open.

1. Which branch for the performance work?

Recommended: a new branch 3.1.9 cut from 3.1.8 after it is submitted. 3.1.8 is the paid build waiting for 15 November and should not take a refactor now.

2. Steps 1–3 now, then measure on the 14 Pro before deciding on step 7?

Recommended: yes. Steps 1–3 are small, touch four views, and change no stored data.

3. Keep Gemma loaded for about a minute after a generation?

Only after step 6's measurement shows load time is a large share and memory stays safe on the iPhone 13.

4. Free Insights layout: one "What Core adds" card instead of separate locks?

Recommended before or right after 15 November, since that is when most users first see Free.

5. Photos as external storage?

Recommended: not now. Revisit if step 4's foreground numbers on the phone are large.
