# Write view audit (3.1.0)

Date: 2026-10-08. Source: a read-only code audit by a subagent of `Features/Write/` (iOS `NoteEditorTextView.swift`, Mac `NoteEditorTextViewMac.swift`, codec, `WriteView*.swift`). Nothing below was run on a device. "Read-verified" means I opened the cited code and the claim follows from it; "agent-reported" means I have not re-read it yet and it must be checked before a fix. Line numbers are as of commit `733bb4f` and drift.

Method: fix in small commits, one regression test per fix (the headless harness in `FormattingCombinationTests.swift` / `ListBackspaceTests.swift` can drive `shouldChangeTextIn`; paragraph-style toolbar conversion needs a first responder, so verify that on device).

Delete Done now asks first ("Delete checked items?") from all three entry points via `WriteView.applyTextCommand`, closing the Aa panel/popover before the alert. | 4 | iOS: inline formatting shifted by one or more characters after list Return, typing into a marker, `1.`+space, a list/heading command, photo deletion, and photo/scan/Talk It Out appends. | **Fixed** (read-verified). Coordinator edits that move the logical text (list Return/exit, typing into a marker, `1. `) now re-read inline ranges via `storeDocuments(from:)`; when the text did not move (style, font, checklist tap) the stored ranges are kept, because those edits replace the paragraph font and reading bold/italic back would lose them. Those four font-replacing edits also re-apply the stored ranges to the new text, so the display keeps bold and the next keystroke no longer saves it un-bolded (this was lost before too). Because stored ranges now follow a paragraph into its new style, formatting the old style supplied must not be stored: extraction (iOS and the Mac codec) now skips Subheading's built-in bold like Title/Heading, and leaving Subheading clears bold over that paragraph in the stored ranges (`NoteEditorCodec.clearingBold`) for entries older builds saved with it. A word the user bolded inside a subheading can't be told apart from the style's bold, so it is not kept. Block Quote is not italic and a checked item only changes colour, so nothing else needed this. `buildLogicalOffsetMap` counts a list marker only when the paragraph starts with it (`displayedMarkerLength`, same rule as `logicalText`). **Inline ranges are not in `parent.text` coordinates when there are photos**: a photo is its one attachment character (none if it failed to decode), not its token. `inlineCoordinateText(from:)` gives that text; checklist Sort/Delete Done (item 3) now remap rows from it, and photo removal adjusts ranges there (`NoteEditorCodec.adjustInlineStyles`), with renumbering a no-op. Photo attach, scan and Talk It Out trim only trailing line breaks (`trimmingTrailingNewlines`). Tests: `InlineOffsetsAfterListEditsTests` (Return, marker typing, `1. `, list on/off/switch with bold in the same paragraph, photo delete, Delete Done below a photo, subheading bold not stored and dropped on leaving, trailing trim), 3 `adjustInlineStyles` and 1 `clearingBold` codec tests, and the subheading fixture now compares inline ranges iOS vs codec. The list on/off/switch and photo tests fail on 30c2b6f, the subheading tests on a0c0e1b. Full target 673 passed, 0 failed (27 opt-in harness skips); Mac self-test 45/45. One earlier full run missed the `NoteEditorRenderCostTests` 5k budget (5.9 ms vs 4 ms; it measures `logicalText`/`displayTextEquivalent`, untouched here); run alone that suite crashes because it isn't `@MainActor`. **Not covered:** the checklist-tap path (needs a tap location); removing a photo line still leaves its paragraph-style slot (item 2). |

## Open, ranked

**Data loss or corruption**

| # | Defect | Verification |
|---|---|---|
| 2 | iOS: entries with a mid-text photo can shift or lose paragraph styles and bake list markers (`logicalText` uses display offsets that include the inflated photo placeholder; two paragraph-index slots per photo line). Repro: a Heading below a mid-text photo, reopen. No round-trip test exists. **Read-verified part (while fixing 4):** iOS stores inline ranges in display-minus-markers coordinates, where a photo is one attachment character (none if it failed to decode), not its `[[mirror-photo-N]]` token, so after a mid-text photo they are not `parent.text` offsets. The `// logical text coordinate` comment on `InlineStyleRange` and the codec header ("both in logical coordinates") are wrong for such entries. Before fixing, grep every reader of `decodeInlineStyleDocument` / `applyInlineStyles` (reader view, search marks, export) that applies ranges to `parent.text`. Also confirmed: a photo line takes two paragraph-style slots (renderer counts the segment before and after the token separately). | partly read-verified |

**Performance (not measured at 50k)**

- Per keystroke: `logicalText`, style encode and inline extract in `textViewDidChange`; `strippedWordCount` in `WriteViewModel.text.didSet` (full `.byWords` segmentation for Japanese and Chinese); `logicalText` and `displayTextEquivalent` again in `updateUIView`.
- `logicalText` sorts photo tokens with `String.distance` comparators (O(n) per comparison); tokens already arrive in order.
- List Return and checklist taps re-render everything, decoding every photo with `UIImage(data:)` on the main thread.
- The editor measures the full document each pass (`isScrollEnabled = false`).
- `NoteEditorRenderCostTests` stops at 10k characters on unstyled text.
- Formatting-only edits never schedule a draft save (`WriteView.swift` watches `text` only); photo changes rewrite all photos on the main actor.

**Polish and accessibility**

- Keyboard-dismiss button has no accessibility label; toolbar icons use fixed point sizes.
- iOS checklist toggle is tap-only (no VoiceOver action); Mac checkboxes have `accessibilityDescription: nil`.
- `insertPhotoToken` is dead code (`.photo(index:)` is never sent), so photos always go at the end.
- `print("[scrollDiag]…")` in `NoteEditorTextView.swift` is intentional (logs caret geometry only, no text); the audit called it stray. Leave it.
