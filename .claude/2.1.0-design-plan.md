# mirror 2.1.0 — UI + LLM output design plan

Scope for 2.1.0 per user direction (2026-09-04): improve UI (including widgets) and improve
on-device LLM output (daily nudge, weekly digest, monthly report). No new `@Model`/CKRecord types
unless a specific item below is explicitly approved to add one (re-arms the manual CloudKit
schema-deploy gate — see `project_cloudkit_schema_deploy` memory).

This file follows the `.claude/loop-state.md` convention: read fully before starting work,
append to Log, don't re-propose something already marked done/discarded.

## Track A — LLM output quality

**The problem with "improve the output" as a goal: it's unfalsifiable without a way to measure
it.** Current prompts (`InsightService.swift`) have zero fixtures and zero output assertions —
only judged by eyeballing real runs. Fix the measurement gap before touching prompt text, or
"improved" is just "different."

### A1. Structural test harness (prerequisite — do this first)

Build a fixture-based test target modeled on `PerformanceXCTests.swift`'s OLD-vs-NEW pattern, but
asserting *structure*, not performance. Fixtures = 4-6 synthetic entry sets (a good week, a rough
week, a mixed month, an edge case — single entry, entries in a non-English locale) checked into
`mirrorTests/Fixtures/`.

Assertions, mechanically derivable from the existing rule text in each `_SYSTEM` prompt:

- **`WEEKLY_DIGEST` / `MONTHLY_REPORT`** (format-contract prompts): all required section labels
  present in order, zero stray `[`/`]`, no Markdown (`#`, `-`, `*` at line start), per-section
  word count under the stated cap (70 words / 45 words)
- **All five prompts**: no first-person leakage outside quotes (`\bI feel\b`, `\bI've been\b`,
  `\bI'm trying\b`, `\bmy \w+\b` not inside `"…"`), banned clinical phrases absent (`this
  suggests`, `patterns indicate`, `the source mentions`, `emotional weariness`, `significant`)
- **`DAILY_NUDGE`**: 2-3 sentences, under 100 words, first sentence names something concrete
  (heuristic: contains a capitalized noun or quoted phrase from the fixture, not a generic opener
  like "It sounds like" / "This week")
- **`EMOTION_DETECT`**: output is exactly one token, member of `MirrorTheme.moodOptions`
- **`ASK`**: 3-5 sentences; when the fixture has zero relevant content, output equals (or closely
  matches) the locale's `askNoAnswerPhrases` entry

Run these against whichever engine is live in CI-equivalent (Gemma 3 1B via `LocalLLMService`
directly, bypassing `FoundationModelEngine` — CI has no Apple Intelligence device). This can't run
in the cloud loop sandbox (no on-device model); it's a local-only test target, run via
`xcodebuild test`.

### A2. Diagnose before prescribing

Run A1's fixtures against the *current* prompts first. Count which rules actually get violated,
and how often. Do not rewrite prompt text based on a guess about what's wrong — the fixture run is
the diagnosis.

### A3. Prompt revision — subtract before adding

Working hypothesis to verify against A2's counts, not assume: `DAILY_NUDGE_SYSTEM` carries 13 rule
bullets, `WEEKLY_DIGEST_SYSTEM` 14, most phrased as negations ("do not", "never", "avoid"). Gemma 3
1B is small; rule-stacking past a point tends to *lower* adherence, and small models generally
follow one strong worked example far better than a long prohibition list. If A2 shows scattered
violations across many different rules (not concentrated in 1-2), that's the signature of
rule-overload, not a missing rule — the fix is:

1. Cut every rule A2 shows is *never* violated (dead weight, remove).
2. Collapse overlapping rules (e.g. the "no first-person leakage" + "no clinical phrases" +
   "sound human" triad in every prompt could be one shared few-shot example block reused across
   prompts instead of restated per-prompt).
3. Add ONE worked example (a fixture entry → a gold-standard nudge/digest) per prompt, replacing
   2-3 prohibition bullets it makes redundant.
4. Re-run A1 after each change — one change at a time, not a rewrite-everything pass, so a
   regression is attributable.

### A4. Validate-and-retry for format-contract prompts

`WEEKLY_DIGEST` and `MONTHLY_REPORT` have a fully parseable contract (fixed section labels in
order). Add a Swift-side validator in `InsightService` that checks the A1 structural assertions
against the real model output before caching it; on failure, retry once with a short corrective
follow-up ("your last answer was missing the WATCH OUT FOR section — retry, six sections, no
brackets") before falling back to the existing error path. This is strictly additive to the
existing 24h-cache flow — validate before the `Insight` is written to SwiftData, not after.

### A5. Context selection

Independent of prompt wording: which entries get packed into the 4,600-6,200 char budget
(`dailyNudgePromptBudget`/`weeklyDigestPromptBudget`/`monthlyReportPromptBudget`/
`askPromptBudget`) changes output quality on its own. Audit the current selection logic (likely
recency-only truncation — confirm by reading the context-assembly code before assuming) against a
long-history fixture; consider weighting toward entries with detected mood extremes or higher word
count over pure recency, since those are more likely to be substantive.

### A6. Per-engine attribution

`InsightService` "never knows which engine actually ran" (Foundation Models vs Gemma fallback) —
today a quality regression report can't be traced to which engine produced it. Add a lightweight,
non-PII engine tag alongside the cached `Insight` (e.g. `Insight.generatedByEngine: String`, values
`"foundation"` / `"gemma"` — a new field on an existing `@Model`, not a new record type, so it
doesn't trip the CloudKit schema gate the same way a new model would... but confirm with the user
before adding any field to a synced model, since even a field addition to `Insight` still needs a
schema check). Surfacing this is for internal diagnosis only — never show engine name to the user,
matches "InsightService never knows which engine ran" being an intentional abstraction at the UI
layer.

**Sequencing: A1 → A2 → A3 (iterative, one prompt at a time, re-verify with A1 each time) → A4 →
A5 → A6.** A3 is the highest-effort, highest-payoff item but only has a target once A2 exists.

## Track B — UI

**Constraint, non-negotiable:** `MirrorTheme.swift` is a mature, deliberate design system — ink
surface tokens (`inkBase/inkMid/inkRaised/inkBorder`), three card elevations
(`inkSurface`/`inkCard`/`inkHero`), the Classic/Sentinel dual theme via `themedCard`/
`themedHeroCard`, a fixed mood color palette, `MirrorTheme.mono()` as the one Sentinel-only type
role. **Every item below extends these tokens. None replace or duplicate them.**

**Every UI item must specify both Classic and Sentinel treatment before it's actionable.**
CLAUDE.md flags every `appDisplayMode` branch as a silent-divergence site — an item that only
describes one theme isn't a complete item, it's half of one.

**Standing constraint from `feedback_standalone_features` memory:** new surfaces get their own
sheet/storage/entry point, not another card bolted onto `InsightView` (already 1,390 lines) or
`MonthlyReportView` (653 lines). Where an item below is a genuine new surface, it should be scoped
as one from the start, not grown inside an existing mega-view.

### B1. Insight-screen legibility pass (not a redesign — a legibility audit)

`InsightView.swift` has accreted sections (nudge, past nudges, mood chart, digest, exploration)
over multiple releases without a legibility pass. Concrete candidates to verify against the actual
rendered screen before committing to any:
- Visual hierarchy between `nudgeSection` (today's actual insight) and `pastNudgesSection` — confirm
  today's nudge reads as unmistakably primary, not same-weight as history.
  Classic: hero card via `themedHeroCard` (already used for the featured moment) vs `themedCard` for
  history rows — check current usage matches this intent. Sentinel: same hierarchy via
  `ViewfinderCorners` (hero-only) vs plain hairline panel.
- Section-to-section rhythm/spacing consistency — audit, don't assume broken.

### B2. Weekly digest / monthly report presentation

`WeeklyDigestView.swift` (283 lines) and `MonthlyReportView.swift` (653 lines) render the six
fixed-format sections from Track A's prompts. Once A3 lands better-structured output, the display
layer should be revisited to match — e.g. each of the six sections as its own visually distinct
block (icon + label treatment per section, consistent with the mood-color language already used
elsewhere) rather than continuous prose. Sequence this AFTER Track A, since the display should be
built against the actual post-A3 output shape, not the pre-revision one.
Classic: card-per-section using `inkSurface`. Sentinel: HUD-style labeled panels, mono type role
for the section headers (`MirrorTheme.mono`), consistent with `sentinelStatusLine`'s existing
pattern in `InsightView`.

### B3. Mood/Brain/Insights navigation coherence

`MoodTimelineView` (938 lines), `BrainView` (513 lines + 4 supporting files), `MonthlyReportView`,
`AskView` are all Deep-tier destinations reachable from `InsightView`'s `explorationSection`. Audit
whether that entry-point pattern reads as a coherent "Deep tier hub" or a flat list with no
grouping — if the latter, consider a lightweight section grouping (not a new tab, not a new
`@Model`) inside the existing exploration section.

**Do not treat B1-B3 as commit-blind.** Each needs a screenshot pass against the live simulator
(`/run` skill) before/after — this is a legibility/hierarchy problem, and hierarchy problems are
only real once seen rendered, not read as prose.

## Track C — Widgets

**The binding constraint here is structural, not visual — read this before proposing any new
widget.**

1. The widget extension target has **no access to `MirrorTheme`**. Every widget file hand-copies
   the handful of hex values it needs (see `DailyNudgeWidget.swift:14-24` — `wBgTop`/`wViolet`/
   `wEmber`/etc., commented as "widgets run in a separate extension target with no access to the
   app's MirrorTheme"). A palette change today is an N-place manual edit across 5 widget files with
   no compiler check that they stay in sync. **Before adding new widget UI, consider extracting a
   `WidgetTheme.swift` shared via a Swift Package or a target-membership-shared file** (both
   `mirror` and `MirrorWidgetExtensionExtension` targets include it) so the palette has one source
   of truth. This is infrastructure, not a visual change, and should land before or alongside any
   widget visual polish, not after.
2. All widget content crosses the App Group boundary through `UserDefaults(suiteName:
   "group.com.lokesh.mirror")` keys, written from the main app and read in the widget. Current key
   inventory (from `mirrorApp.swift`/`ContentView.swift`/`SubscriptionService.swift`):
   `widget.nudge.text` / `widget.nudge.date`, `widget.entries.heatmap`, `widget.mood.heatmap`,
   `widget.streak`, `widget.wrote.today`, `widget.displayMode`, `widget.tier`. **Any new widget
   content needs: a new key, a write site in the app (with the matching
   `WidgetCenter.shared.reloadTimelines(ofKind:)` call), and a tier-gating decision** — enumerate
   this triplet per idea below, don't hand-wave it.

### C1. Weekly Digest widget (new)

Home-screen surface for the weekly digest, same tier gate as `MirrorNudgeWidget` (Core+). Bridge:
`widget.digest.theme.text` (just the THIS WEEK'S THEME section — full six-section digest doesn't
fit a widget), `widget.digest.weekIdentifier`; write site alongside the existing
`InsightService`/SwiftData digest-generation path (Sunday `BGAppRefreshTask`), reload
`MirrorWeeklyDigestWidget` kind on write. Small family only (theme line + "Weekly Digest" label,
same visual grammar as `NudgeSmallView`). Classic: serif quote-mark treatment matching
`NudgeSmallView`. Sentinel: mono BRIEFING-style label, ember hairline.

### C2. Monthly Report teaser widget (new, Deep-only)

Medium family, shows `YOUR MONTH IN ONE IMAGE` (the single-sentence metaphor — the most
widget-appropriate of the six sections). Bridge: `widget.monthlyReport.image.text`,
`widget.monthlyReport.periodIdentifier`; write site alongside monthly-report generation
(`BGProcessingTask` nightly pass / manual regenerate). Tier gate: `widget.tier == "deep"` only,
reusing the existing locked-state pattern (`NudgeLockedView` precedent) but priced as Deep
($4.99/mo), not Core.

### C3. Existing widget upkeep

Once C-infra (WidgetTheme extraction) lands, do a pass over all 5 existing widgets
(`WriteWidget`/`DailyNudgeWidget`/`EntriesMapWidget`/`MoodMapWidget`/`WritingPromptWidget`) to
migrate off their hand-copied hex constants onto the shared theme source — mechanical, low-risk,
but only worth doing once the shared source exists (doing it widget-by-widget first just recreates
the N-place-edit problem for the *next* palette change).

**Sequencing: infra (shared WidgetTheme) → C1 → C2 → C3.** C1/C2 are genuinely new widgets, so per
`feedback_standalone_features`, each gets its own bridge keys and its own `Widget` struct — not
folded into `MirrorNudgeWidget`'s existing dispatcher.
