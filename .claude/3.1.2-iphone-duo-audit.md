# iPhone Duo audit (3.1.2)

Started 2026-10-11. Plan: `3.1.2-iphone-duo.md`.

**Method:**
- An isolated copy (`.searchdev` bundle, CloudKit off, synthetic `--perfSeed` journal plus seeded insights) on the iPhone Duo simulator (Xcode 27.1, iOS 27.1).
- Driven by a throwaway XCUITest (`DuoAuditUITests`, in the copy only) and captured per screen.
- Fold state can only be changed by hand in DeviceHub (no `simctl` or accessibility control), so the owner switches poses between runs.
- The test captures the screen that is lit. Inner-screen captures come out in the panel's native orientation and are rotated for review.

## Findings
### Must-fix
- **F1. The mood/tag chip row ignores the side safe area.** On the closed screen the "Peaceful" chip rests under the clock in the status strip. On the opened screen, "Energized" passes under the Wi-Fi icon. It's an interactive row, and Apple says interactive elements must not sit behind side controls. Likely the same for the week calendar strip (F5). Fix: keep the row's background full-bleed but inset its content with the safe area (`contentMargins` / safe-area padding).
- **F2. Sentinel sidebar.**
  - `AppSidebarItem.title` is fixed to Entries / Write / Insights / Settings, so the opened Duo in Sentinel shows Classic names, not Log / Transmission / Briefing.
  - The sidebar keeps the system grey background, not Sentinel ink.
  - The Settings page is titled "Config" while its sidebar row says "Settings".
  - iPad had this too, but on the Duo every user who opens the phone sees it.

### To verify (needs another run)
- **F3. Opening or closing the phone rebuilds the whole screen** (`ContentView` swaps `TabView` ↔ `NavigationSplitView` on the size class).
  - **Verified 2026-10-11** (open → closed, with draft saving on): the typed text survived, the caret stayed at the end, the keyboard stayed up, and the status showed "Draft saved".
  - Still lost:
    - **undo history** (the undo arrow was active before the fold and greyed after);
    - anything typed in the last 0.9 s before folding (the autosave debounce);
    - from code, also open sheets, scroll position and a pushed reader (not yet captured).
  - The first run, closed → open, lost the text, but it was invalid: synthetic-journal mode turns draft saving off unless `--scratchDraftStorage` is passed.
  - The one-`TabView` fix in the plan keeps the same views across the fold, so none of this is rebuilt.
- **F4. Formatting panel on the opened Duo.** `WriteView.usesPopoverPanel` (`userInterfaceIdiom == .pad`) and `NoteEditorTextView.swift:3406` pick the iPhone path (the panel replaces the keyboard) on a 951 × 669 pt screen. It works (captured in Sentinel), but on that screen a popover off the Aa button is the iPad behaviour Apple's guidance points to. Fix: decide by available width, not idiom.

### Should-fix / design
- **F8. Opened portrait hides the sidebar.** `NavigationSplitView` shows it as an overlay that dims the content, so switching sections takes two taps (show the sidebar, then pick). The approved one-`TabView` (`sidebarAdaptable`) fix gives portrait a tab bar instead.
- **F7. Global window lookups** (Apple's resizability skill, "never walk global scene state"):
  - `NoteEditorTextView.swift:368`: photo Share presents from the *first* scene's root view controller. It can fail silently if a sheet is already up or another window is in front. Present from the editor's own view controller.
  - `AskView.swift:689`: the keyboard overlap uses the active key window. It already converts into window space (Split View-safe), so the risk is low.
  - The rest are fine: `ContentView.swift:104` (appearance on every scene), `ReviewRequestManager`, `RateUsPromptSheet`, `PlatformCompat`.
- **F5. The week calendar strip is clipped at both edges** on the wide screen (seen in the owner's screenshot and in the captures). It reads as cut off rather than scrollable.
- **F6. Wide screen space is mostly empty.**
  - Entries rows stretch about 850 pt for 2–3 lines.
  - The reader card uses about 60% of the width.
  - Insights is one stretched column.
  
  These are the two-column opportunities in the plan (Phase 3).

### Fine as is
- Closed screen: the system puts the status bar, tab bar, toolbar buttons and back button in the right strip, and content stays clear. Write, the format panel (it spans the strip, like a keyboard), Insights, the Today card, the digest and the Mood Timeline all fit, in both themes. Sentinel's corner brackets stay clear of the strip.
- Opened screen: sidebar switching works, including from an open entry back to Write or Insights. The keyboard and Write fit. The reader's back button is in the strip. Settings is fine.
- App Lock reads the real biometry type (`AppLock.swift:61`), so the Duo should show Touch ID (not yet seen).
- No `UIScreen.main`, orientation APIs, fixed sizes or `UIWindow(frame:)` anywhere.
- UIKit has `UIHinge` / `UIHingeStatus` (closed, partiallyOpen, fullyOpen) if a pose-aware layout is ever wanted. Apple's guidance is to rely on size classes instead.

## Apple's resizability skill (`xcrun agent skills export` → `app-resizability`)
- **Prerequisites: all pass.**
  - Launch screen: `INFOPLIST_KEY_UILaunchScreen_Generation = YES`.
  - iPad declares all four orientations.
  - No `UIRequiresFullScreen`.
- **Code patterns:**
  - `UIScreen.main`: none.
  - Orientation: none.
  - `userInterfaceIdiom`: 2 (F4).
  - Asymmetric safe areas: 3 bottom-inset reads only (Ask keyboard, mood check-in, rate prompt). Fine, since the Duo's asymmetry is left/right.
  - Scene lifecycle: SwiftUI `App` with `@UIApplicationDelegateAdaptor`; the delegate only handles background model downloads (`handleEventsForBackgroundURLSession`).
  - Global scene lookups: 6 (F7).

### Full skill pass (2026-10-11, after reading all five task references)
- **Scene lifecycle:** not needed. SwiftUI `App` + `WindowGroup` is scene-based (the task's "already migrated" case).
- **Orientation:** no uses.
- **UIScreen:** no uses.
- **Idiom (F4):**
  - `WriteView.usesPopoverPanel`: the skill's SwiftUI rule is `horizontalSizeClass == .regular`. Test `.regular`, never `!= .compact`.
  - `NoteEditorTextView` (a `UIViewRepresentable`): read `context.environment.horizontalSizeClass` in `make`/`updateUIView`.
  - Caveat from the file's own comment: inside an iPad `NavigationSplitView` detail the size class reported `.compact`. Re-check that on iPad after the one-`TabView` change.
- **Safe areas (Rule 13, SwiftUI):**
  - `ignoresSafeArea` uses are backgrounds, scrims, the 3D Brain backdrop, or system pickers in sheets. All allowed.
  - Sentinel's `ViewfinderCorners` overlay in Write uses design-value padding inside the safe area. Allowed.
  - Inset reads are bottom-only.
- **F1 likely cause:** the Entries header row sets `listRowInsets(EdgeInsets(top: 0, leading: 0, bottom: 8, trailing: 0))` (`EntryListView.swift:875`), so its horizontal chip and week rows run to the cell edges, under the side strip. Fix per the skill: let the row honour the safe area, and keep any edge-to-edge look through scroll content margins, not zero row insets.
- **New iOS 27.1 APIs the skill names:** `@Environment(\.toolbarVerticalEdge)` (SwiftUI: which edge holds the vertical bar) and `traitCollection.verticalBarEdge` (UIKit). Use them only if a layout must know the bar's side; safe areas usually cover it.
- **Not yet checked by the skill rules:** Brain View's zoom controls (in a `ZStack` over the full-bleed scene; they should respect the safe area), and the custom Write top bar on the closed screen.

## Fix status (2026-10-11)
- **F1: not a bug.** Scrolled to the end on the closed Duo, the last chip ("Numb") stops clear of the strip with its normal padding. The horizontal scroll view already insets its end, and the row only passes under the strip at rest, as list rows do under a toolbar. No change.
- **F4: fixed.** `WriteView.usesPopoverPanel` = `horizontalSizeClass == .regular`, passed into the editor (`panelAsPopover`) so the SwiftUI popover and the UIKit `inputView` panel can't disagree. The old idiom checks are gone.
- **F7: fixed.** `presentShareSheet(items:from:rect:)` presents from the anchor's own window (else the foreground key window), on top of anything already presented, with a popover source. The editor's photo Share anchors at the long-pressed spot. Reader and entry-list shares use the same helper without an anchor, so they also gain the top-presenter and popover-source fixes; before, they could fail on iPad and the opened Duo, where a popover needs a source.
- **F4/F7 verified (2026-10-11):**
  - **iPad simulator:** the format panel is a popover off Aa with the keyboard up. Reader → More → Share opened without a crash (the test asserts the reader and the Share item).
  - **iPhone 14 Pro:** the format panel still replaces the keyboard, unchanged.
  - Not yet seen on the opened Duo (regular width, so it should match iPad).
